MC OpenAPI is a JSON-over-HTTPS API. Every call targets a gateway host under `/openapi/v1/`, carries the required signing headers, and — where applicable — a JSON body. Envelope fields depend on the response source: business services, a small number of legacy endpoints, and gateway authentication errors do not return identical shapes.

## Request format

### Required headers

Include the following headers on every request:

| Header | Required | Value |
| --- | --- | --- |
| `X-Access-Key` | Yes | Your Access Key ID |
| `X-Signature` | Yes | HMAC-SHA256 signature over the canonical string (**Base64**) |
| `X-Timestamp` | Yes | Current Unix time in **milliseconds** |
| `X-Nonce` | Yes | New value per request; **UUID v4**, or ≥32 hex characters (`0-9a-fA-F`) |
| `Content-Type` | Recommended with a JSON body | `application/json`, including for `DELETE` with a body |
| `Accept` | Recommended | `application/json` |

<Warning>
  Requests without valid signing headers or `X-Nonce`, or with a `X-Timestamp` outside the allowed window, are rejected. Never commit your Secret Key to source control or expose it in client-side code.
</Warning>

See [Authentication](/authentication) for the exact string-to-sign format and reference implementations in Python, Java, and Node.js.

### String to sign (summary)

```text
{HTTP_METHOD}
{REQUEST_URI}
{QUERY_STRING}
{SIGNED_HEADERS}
{TIMESTAMP}
{NONCE}
[{BODY_SHA256_HEX}]
```

- Omit the entire `QUERY_STRING` line when there is no query (do **not** insert a blank line).
- Sign decoded logical query names and values; apply transport encoding separately when sending the URL.
- `SIGNED_HEADERS` includes `x-access-key`, `x-nonce`, and `x-timestamp` (lowercase keys, sorted).
- For `POST`/`PUT`/`PATCH`/`DELETE` with a non-empty body, append the SHA-256 of the raw body bytes as **lowercase hex**.
- `X-Signature` is Base64, not hex.

### Example: query the USD exchange rates

```bash
curl --request GET \
  --url "https://gateway.mcconnects.com/openapi/v1/mc-account/exchange-rate/query/usd" \
  --header "X-Access-Key: $MC_ACCESS_KEY" \
  --header "X-Signature: $MC_SIGNATURE" \
  --header "X-Timestamp: $MC_TIMESTAMP" \
  --header "X-Nonce: $MC_NONCE" \
  --header "Accept: application/json"
```

## Response format

All responses are JSON, but do not assume every endpoint returns the same fields. Treat the response schema on the endpoint page as authoritative.

### Business-service response (primary)

Most Account, Trade, and Aggregator endpoints use this envelope. The following example shows a parameter validation failure:

```json
{
  "status": 400,
  "message": "Invalid request parameter",
  "code": "1000005",
  "codeKey": "PARAM_ERROR",
  "params": {
    "field": "type"
  },
  "localizedMessage": "Invalid request parameter",
  "data": null,
  "success": false
}
```

<ResponseField name="status" type="integer">
  HTTP-style status value carried in the envelope. The actual HTTP status remains authoritative for transport handling.
</ResponseField>

<ResponseField name="message" type="string">
  Default message for logging. Do not branch on its exact text.
</ResponseField>

<ResponseField name="code" type="string">
  Business status code. Its type and success value can vary by service version; use it together with `success`.
</ResponseField>

<ResponseField name="codeKey" type="string">
  Stable business error key, such as `PARAM_ERROR`. Prefer this field for branching when present.
</ResponseField>

<ResponseField name="params" type="object | null">
  Message interpolation parameters. It may be empty when the message has no parameters.
</ResponseField>

<ResponseField name="localizedMessage" type="string | null">
  Message localized for the request language. It may be empty when no localized text is available.
</ResponseField>

<ResponseField name="data" type="object | array | null">
  The actual response payload. Shape depends on the endpoint — a single object, a list, or a paginated page object.
</ResponseField>

<ResponseField name="success" type="boolean">
  Whether the business operation succeeded. Do not infer business success from HTTP `200` alone.
</ResponseField>

### Other response variants

| Source | Fields | Client handling |
| --- | --- | --- |
| A small number of legacy Account endpoints | `code`, `msg`, `data`, `extraFieldMap`, `success` | Fall back to `msg` for the message |
| Risk endpoints | `status`, `message`, `code`, `data`, `success` | Do not assume `codeKey` exists |
| API Gateway authentication errors | `status`, `code`, `message` | Handle by HTTP status and `message`; there is no `success`, `data`, or `codeKey` |

For example, the API Gateway returns this shape when an Access Key lacks the endpoint permission:

```json
{
  "status": 401,
  "code": 401,
  "message": "没有访问该接口的权限"
}
```

### Paginated list response

This example uses the success values from `RetResult.data()`; the exact `data` fields depend on the endpoint schema.

Endpoints that return a page of results place a page object inside `data`:

```json
{
  "status": 200,
  "message": "ok",
  "code": "200",
  "codeKey": null,
  "params": {},
  "localizedMessage": null,
  "success": true,
  "data": {
    "records": [
      { "transactionId": "T-1001", "amount": 125.5, "acSymbol": "USDT" }
    ],
    "total": 132,
    "size": 20,
    "current": 1,
    "pages": 7,
    "hasPrevious": false,
    "hasNext": true
  }
}
```

See [Pagination](/concepts/pagination) for how to request additional pages.

## HTTP status codes

MC OpenAPI uses standard HTTP status codes for transport-level outcomes. Even on a `200 OK`, always inspect the envelope `code` for the business result.

| Code | Meaning |
| --- | --- |
| `200` | Request delivered successfully. Check `code` in the JSON envelope for the business result. |
| `400` | Malformed request — missing parameters or invalid JSON body. |
| `401` | Signature invalid, `X-Timestamp` skewed, Access Key not recognised, or the key lacks the endpoint permission. |
| `404` | The endpoint or resource does not exist. |
| `429` | Rate limit exceeded — see [Rate Limits](/guides/rate-limits). |
| `500` | Unexpected gateway error. Retry with backoff. |
| `503` | Gateway temporarily unavailable. Retry with backoff. |

<Tip>
  Log `code`, `codeKey`, `message` / `localizedMessage` / `msg`, and any correlation ID from response headers on every non-`200` response.
</Tip>
