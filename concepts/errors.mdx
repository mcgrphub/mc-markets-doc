MC OpenAPI reports failures through **two layers**: a standard HTTP status code, and business fields inside the JSON envelope (`code` / `codeKey`). Robust integrations check both.

## Two-layer error model

1. **Transport layer** — the HTTP status code. `4xx` indicates a client problem, `5xx` a gateway problem.
2. **Business layer** — `code` and `codeKey` in the JSON envelope. A `200 OK` HTTP response can still carry a business error such as insufficient balance or a symbol not found.

Always inspect `success` / `code` / `codeKey` even when the HTTP status is `200`.

## Error response format

Business services usually return the full business envelope, while gateway authentication errors use a smaller envelope. See [Requests & Responses](/concepts/request-response) for all variants. This example shows a business parameter error:

```json
{
  "status": 400,
  "message": "Invalid request parameter",
  "code": "1000005",
  "codeKey": "PARAM_ERROR",
  "params": {
    "field": "type"
  },
  "localizedMessage": "Invalid request parameter",
  "success": false,
  "data": null
}
```

<ResponseField name="status" type="integer">
  HTTP-style status value in the envelope. Use the actual HTTP status for transport handling.
</ResponseField>

<ResponseField name="message" type="string">
  Default message for logging. Do not branch on its exact text.
</ResponseField>

<ResponseField name="code" type="integer | string">
  Business status code. Its type and success value can vary by service version; business failures commonly use a 7-digit code.
</ResponseField>

<ResponseField name="codeKey" type="string">
  Stable error key, for example `PARAM_ERROR` or `SIGN_ERROR`. Prefer `codeKey` or `code` when this field exists.
</ResponseField>

<ResponseField name="params" type="object | null">
  Message interpolation parameters. It may be empty.
</ResponseField>

<ResponseField name="localizedMessage" type="string | null">
  Message localized for the request language. It may be empty.
</ResponseField>

<ResponseField name="success" type="boolean">
  `false` on business failures.
</ResponseField>

<ResponseField name="data" type="object | null">
  Usually `null` on errors. Some validation errors include a `data` object with per-field detail.
</ResponseField>

## HTTP status codes

| Code | When it occurs | What to do |
| --- | --- | --- |
| `400` | Malformed JSON, missing required parameter | Fix the request and retry. |
| `401` | Missing / invalid `X-Signature`, `X-Timestamp` skewed, or missing endpoint permission | Re-check signing and the clock. If `message` is `没有访问该接口的权限`, update the key permissions. |
| `404` | Path is wrong, or the resource ID does not exist | Verify the URL and IDs. |
| `429` | Rate limit exceeded | Back off — see [Rate Limits](/guides/rate-limits). |
| `500` / `502` / `503` | Gateway or upstream error | Retry with exponential backoff. |

## Common business codes

Full catalog: [Error codes](/api-reference/error-codes) (public OpenAPI-reachable codes only).

| `codeKey` | `code` | Meaning | Suggested action |
| --- | --- | --- | --- |
| `PARAM_ERROR` | `1000005` | Invalid request parameter | Fix parameters using `message` / `localizedMessage`. |
| `NOT_EXIST` | `1000002` | Resource does not exist | Verify IDs in the request. |
| `ACCOUNT_BALANCE_INSUFFICIENT` | `2004003` | Insufficient balance | Top up or reduce the amount. |
| `ORDER_OPERATION_FAILED` | `2100001` | Order operation failed | Inspect `message` / `localizedMessage`; retry only if transient. |
| `DEFAULT` | `1000000` | Internal server error | Retry with backoff; contact support if it persists. |

<Note>
  AK/SK authentication failures, including permission failures, return `status`, `code`, and `message` from the gateway and have **no** `codeKey`. See [Authentication](/authentication).
</Note>

## Handling errors

### Python

```python
import requests, time

def call(method, path, body=""):
    # ... build signed request as in the auth docs ...
    response = requests.request(method, url, headers=headers, data=body)

    if response.status_code == 429 or 500 <= response.status_code < 600:
        raise TransientError(response.status_code, response.text)

    payload = response.json()
    if payload.get("success") is True:
        return payload.get("data")

    code_key = payload.get("codeKey") or str(payload.get("code"))
    if response.status_code == 401:
        raise AuthError(code_key, payload.get("msg") or payload.get("message"))

    message = payload.get("localizedMessage") or payload.get("message") or payload.get("msg")
    raise BusinessError(code_key, message)


def with_backoff(fn, *args, max_retries=5, **kwargs):
    delay = 1.0
    for attempt in range(max_retries):
        try:
            return fn(*args, **kwargs)
        except TransientError:
            if attempt == max_retries - 1:
                raise
            time.sleep(delay)
            delay = min(delay * 2, 30)
```

### JavaScript

```javascript
async function call(method, path, body = "") {
  // ... build signed request as in the auth docs ...
  const res = await fetch(url, { method, headers, body: body || undefined });

  if (res.status === 429 || res.status >= 500) {
    throw new TransientError(res.status, await res.text());
  }

  const payload = await res.json();
  if (payload.success === true) return payload.data;

  const codeKey = payload.codeKey || String(payload.code);
  if (res.status === 401) {
    throw new AuthError(codeKey, payload.msg || payload.message);
  }
  const message = payload.localizedMessage || payload.message || payload.msg;
  throw new BusinessError(codeKey, message);
}
```

<Tip>
  For `429` and `5xx` responses, use **exponential backoff with jitter**: start at ~1 s, double on each failure, cap at ~30 s, and add a small random offset to avoid synchronized retries.
</Tip>
